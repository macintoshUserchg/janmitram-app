# Payout Module Implementation Plan

## Overview
This plan outlines the implementation of a multi-level marketing (MLM) payout system for shop owners (sellers) in the Janmitram application. The system calculates monthly payouts based on:
1. Phase 1: Direct Shop Earnings - 10% commission on the shop owner's own sales.
2. Phase 2: Group Income Plan - Network-based earnings based on downline sales and group size, with tiered percentage rates.

## Current State
- The application has a wallet and transaction system for managing user balances.
- Shop owners can request withdrawals from their wallet.
- There is no existing MLM or referral structure.
- Commissions exist for admin earnings on orders, but not for shop owner payouts.

## Proposed Changes

### 1. Database Modifications
Add the following columns to the `shops` table:
- `parent_shop_id` (foreign key to `shops.id`, nullable) - to establish the referral/upline relationship.
- `level` (integer, nullable) - to store the calculated MLM level for reporting.
- Optionally, we could add `left_shop_id` and `right_shop_id` if implementing a binary tree, but the requirements suggest a simple tree (unlimited downline).

We'll also create a table to store monthly payout snapshots for history and reporting:
```sql
CREATE TABLE shop_monthly_payouts (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    shop_id BIGINT UNSIGNED NOT NULL,
    year INT NOT NULL,
    month INT NOT NULL,
    personal_sales DECIMAL(15,2) NOT NULL DEFAULT 0,
    group_sales DECIMAL(15,2) NOT NULL DEFAULT 0,
    group_size INT NOT NULL DEFAULT 0,
    level TINYINT UNSIGNED NOT NULL DEFAULT 0,
    phase1_amount DECIMAL(15,2) NOT NULL DEFAULT 0,
    phase2_amount DECIMAL(15,2) NOT NULL DEFAULT 0,
    total_payout DECIMAL(15,2) NOT NULL DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (shop_id) REFERENCES shops(id) ON DELETE CASCADE
);
```

### 2. Model Updates
- Update the `Shop` model to define relationships:
  ```php
  public function parent(): BelongsTo
  {
      return $this->belongsTo(Shop::class, 'parent_shop_id');
  }

  public function children(): HasMany
  {
      return $this->hasMany(Shop::class, 'parent_shop_id');
  }

  public function monthlyPayouts(): HasMany
  {
      return $this->hasMany(ShopMonthlyPayout::class);
  }
  ```
- Create a new `ShopMonthlyPayout` model.

### 3. Service Classes
Create a `PayoutService` (or similar) that contains the core logic:
- Calculate personal sales for a shop for a given month (sum of order totals where shop_id = shop.id and order created in that month).
- Calculate downline (all descendants in the shop tree) recursively.
- Calculate group size (count of active shops in downline + self) and group sales (sum of personal sales of all shops in downline + self).
- Determine the level based on group size and group sales using the provided table.
- Compute phase 1 amount: personal_sales * 0.10.
- Compute phase 2 amount based on level:
  - Level 0: if group_size >= 10 and group_sales >= 33000 → 3000 else 0
  - Level 1: if group_sales between 33000 and 300000 and group_size >= 10 → group_sales * 0.04
  - Level 2: if group_sales between 300000 and 3000000 and group_size >= 100 → group_sales * 0.01
  - Level 3: if group_sales between 3000000 and 30000000 and group_size >= 10000 → group_sales * 0.002
  - Level 4: if group_sales >= 30000000 and group_size >= 100000 → group_sales * 0.0004
  - Level 5: if group_sales >= 30000000 and group_size >= 100000 (and meets leadership criteria, which we'll approximate as same as level 4 for now) → 150000 fixed
  - Otherwise: 0
- Total payout = phase1 + phase2.
- Credit the shop's wallet with the total payout amount as a transaction (type: credit, purpose: 'mlm_payout').
- Record the snapshot in `shop_monthly_payouts`.

### 4. Artisan Command
Create a console command `mlp:calculate-payouts` that:
- Determines the previous month (or accepts a month/year argument).
- Iterates over all shops (or only active shops) and calculates their payout for that month using the PayoutService.
- Logs results or outputs summary.
- Can be scheduled to run monthly via cron.

### 5. API Endpoints (Optional)
For shop owners to view their earnings:
- GET `/api/seller/payouts` - returns paginated monthly payouts for the authenticated shop.
- GET `/api/seller/payouts/{id}` - returns details of a specific month.
These could be added to the existing `API/Seller/DashboardController` or a new controller.

### 6. Frontend Updates (Optional)
- Add a section in the shop dashboard to show monthly earnings and payout history.
- This would require Blade/Vue components, but since the task is backend-focused, we may skip UI or note it as future work.

### 7. Testing
- Write unit tests for the PayoutService methods.
- Test edge cases (e.g., no downline, boundary values for levels).
- Test the artisan command.

### 8. Scheduling
- Add the command to the scheduler (`app/Console/Kernel.php`) to run on the first day of each month at 00:00.

## Assumptions and Open Questions
1. **Active Shop Definition**: What constitutes an active shop for downline counting? We'll assume a shop is active if its associated user is active (`is_active = 1`) and the shop itself has a status of 1 (or similar). We may need to clarify.
2. **Leadership Criteria for Level 5**: The description says "Defined by business rules (scale + leadership qualification)". We'll assume that meeting the level 4 thresholds (sales >= 30M, group size >= 100k) qualifies for level 5, but we may need additional criteria. We'll note this as needing clarification.
3. **Time Period for Sales**: We'll use calendar month for simplicity, but the business might use a rolling 30-day period. We'll assume calendar month unless specified otherwise.
4. **Duplicate Counting**: Ensure that when calculating group sales, we do not double-count sales. Each shop's personal sales are summed once.
5. **Currency**: All amounts are in Indian Rupees (₹). We'll use decimal with precision 2.

## Notes
- The plan focuses on the backend logic and data storage.
- Frontend updates are out of scope for this plan but should be considered for a complete feature.
- Performance considerations: For large downlines, recursive calculation may be slow. We may need to implement a materialized path or nested set in the future. For now, we assume the network size is manageable.
- The payout is credited to the wallet as a credit transaction, which can then be withdrawn via the existing withdraw flow.
